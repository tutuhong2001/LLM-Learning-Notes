# 设计说明：一个能讲清楚的最小 RAG

## 为什么选择这个范围

本项目解决“从自己的 AI 学习笔记中找依据并回答”的小问题。核心只有三件事：检索资料、组装有来源的提示词、测量检索是否找对。通过同一接口比较 BM25 与 Sentence-Transformers，可以说明词法检索与语义检索的区别。

没有引入 LangChain：当前流程是一次检索加一次生成，直接使用 SDK 更容易看到数据流。以后出现多轮状态、多个工具或复杂路由时，再评估框架收益。也没有把固定链路称为 Agent，因为它没有自主规划或工具选择循环。

## 实现决策

| 决策 | 原因 | 代价 |
| --- | --- | --- |
| 短 Markdown 文件作为检索单元 | 易读、方便人工核对与引用 | 不适合直接塞入长文档 |
| 保留 BM25 基线 | 无依赖运行，精确术语匹配可解释 | 同义改写能力有限 |
| 使用中文 BGE 小型编码器 | Sentence-Transformers API 简洁，CPU 可运行 | 首次下载权重，需要模型网络访问 |
| 归一化向量后用点积排序 | 对小知识库足够，数学直观 | 每次启动重新编码，规模大时慢 |
| 生成走 OpenAI 兼容 API | 本地无需部署生成式大模型 | 依赖外部服务，会发送选中的资料 |
| 引用编号回指文件 | 方便人工检查依据 | 编号有效不等于语义上有依据 |

## 数据流

`load_documents` 读取短文档 → 检索器建立统计量或编码向量 → `search` 返回排序后的 Hit → `build_messages` 编排来源编号 → `generate_answer` 请求模型 → 展示回答并检查引用编号。

`--dry-run` 会停在请求内容预览，绝不把检索片段拼接伪装成模型回答。

## 适用边界

- 适合学习演示、小规模公开笔记；不是生产问答系统。
- 没有做通用文档解析、长文档切分、索引持久化或多用户权限。
- BM25 只要有词重合就可能返回弱相关结果；语义检索总会给出最近邻。
- 没有校准“可回答性”分数阈值，知识库外问题主要依赖模型遵守拒答提示。因此未知问题拒答并无可靠保证。
- 提示词注入防护仅是提示层约束；没有宣称安全隔离。
- 各模型的 token 上限与输入指令不同。更换模型时应检查模型卡。

## 下一步优先顺序

1. 增加真实问题、无答案问题和独立标注，先发现错误类型。
2. 对长文档补充分块与来源片段编号，再加入持久化缓存。
3. 根据误差分析选择混合检索或 reranker，并比较准确率与延迟。
